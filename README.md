## Getting started

Run the following command to generate and compile your parser, and then run all the provided tests:

```bash
mvn clean package

java -cp "chocopy-ref.jar:target/assignment.jar" chocopy.ChocoPy --pass=s --test --dir src/test/data/pa1/sample/
```

In the starter code, only one test should pass. Your objective is to build a parser that passes all the provided tests and meets the assignment specifications.

To manually observe the output of your parser when run on a given input ChocoPy program, run the following command (replace the last argument to change the input file):

```bash
java -cp "chocopy-ref.jar:target/assignment.jar" chocopy.ChocoPy --pass=s src/test/data/pa1/sample/expr_plus.py
```

You can check the output produced by the staff-provided reference implementation on the same input file, as follows:

```bash
java -cp "chocopy-ref.jar:target/assignment.jar" chocopy.ChocoPy --pass=r src/test/data/pa1/sample/expr_plus.py
```

Try this with another input file as well, such as `src/test/data/pa1/sample/coverage.py`, to see what happens when the results disagree.

### Question 1: How are INDENT and DEDENT tokens emitted?

File `src/main/jflex/chocopy/pa1/ChocoPy.jflex`, core lines **162-192**
(rule at the start of a line) and **283-298** (end of input), with the
indentation stack and the tab rule at lines **83-103**.

The lexer has two states. `YYINITIAL` means "at the beginning of a physical
line", `LINE_BODY` (declared on line 31) means "inside a logical line". In
`YYINITIAL`, lines that contain only whitespace and/or a comment are matched
including their line break and skipped, so they never produce NEWLINE,
INDENT or DEDENT. Otherwise the rule `{WhiteSpace}* [^ \t\r\n#]` matches the
leading whitespace together with the first real character; that character is
pushed back with `yypushback(1)`, and the indentation of the whitespace is
computed (a tab advances to the next multiple of 8). As in the manual, we
keep a stack of indentation levels that starts with 0:

- larger than the top: push it, switch to `LINE_BODY`, return one INDENT;
- equal: switch to `LINE_BODY` and return nothing;
- smaller: pop one level, return one DEDENT and push back the whole
  whitespace (`yypushback(width)`), so the same rule fires again on the next
  call and emits the next DEDENT, until the level matches.

The trick of pushing the input back lets a single JFlex rule return several
tokens for one line without a separate token queue. In `LINE_BODY` a line
break returns NEWLINE and switches back to `YYINITIAL`. At the end of the
input the `<<EOF>>` rule first emits a NEWLINE if the last line had no line
break, then one DEDENT per open level, then EOF. INDENT and DEDENT tokens
span the leading whitespace of their line, so that block statements end at
the same location as in the reference implementation.

### Question 2: What was the hardest language feature?

Reproducing the exact source locations of the reference implementation,
in particular for `if`/`elif`/`else` chains, function definitions and the
`Program` node: file `src/main/cup/chocopy/pa1/ChocoPy.cup`, lines
**149-163** (`start_program`, together with `scan()` on lines **46-61**),
**202-210** (`function_definition`) and **292-309** (`compound_statement`,
`if_tail`), with the helper class `IfTail` on lines **11-19**.

The hidden tests compare the complete JSON output, so every location has to
be equal, and the reference does not always use "from the first to the last
token of the rule":

1. *elif chains.* The AST has no elif node: `elif b: ...` becomes an `IfStmt`
   that is the only statement of the else body of the enclosing `IfStmt`.
   Both nodes end at the DEDENT of the *last* block of the whole chain, which
   the outer rule has not seen yet when its first block is finished. We
   therefore parse the rest of the chain into the nonterminal `if_tail`,
   which returns an `IfTail` object holding the else body together with the
   end location of its last DEDENT. Each level takes its end from the tail,
   or from its own DEDENT if there is no tail, so for
   `if a: ... elif b: ... else: ...` both `IfStmt` nodes end at the same
   position.
2. *Functions.* A `FuncDef` ends where the NEWLINE of its last statement
   ends, not at the DEDENT like a block statement, so its end is taken from
   the `function_body` symbol and not from the DEDENT token. A function
   without `->` gets the return type `ClassType` `<None>`, which the reference
   places at the colon of the header with zero width, e.g. `[1, 8, 1, 8]`
   for `def f():`.
3. *The program.* `Program` starts at its first token and ends where its
   last NEWLINE or DEDENT ends. This cannot be computed from the two lists
   alone: a program that contains only `pass` statements has an empty
   statement list but still a location. The parser therefore overrides
   `scan()`, which hands every token from the lexer to the parser, and
   records the start of the first token and the end of the last NEWLINE or
   DEDENT; `start_program` builds the `Program` node from these two
   positions, and an empty file gets `[0, 0, 0, 0]`.

To find these cases we compared every location of our output with the
reference on more than 11,000 programs (see *Testing*). Error recovery uses
the `error` symbol at the statement level (`statement ::= error NEWLINE`)
and for broken `def` and `class` headers (`DEF error NEWLINE INDENT
function_body DEDENT`, `CLASS error NEWLINE INDENT class_decl_list DEDENT`),
so the body of a broken function or class is still parsed and the rest of
the program is checked. The first error is always reported at the same
token as in the reference parser.

### Bug reports and remarks on the course material

1. **The reference lexer does not terminate the last line at end of input.**
   The manual (3.1.1) says that the end of the input also terminates the
   last physical line. For the input `x = 1` without a final line break,
   `java -cp "chocopy-ref.jar;target/assignment.jar" chocopy.reference.ChocoPyLexer`
   prints `INTEGER` followed directly by `EOF`, without a `NEWLINE`, and
   `chocopy.reference.RefParser.process("x = 1", false)` reports
   `Parse error near token EOF`. Expected: a NEWLINE token and the AST of
   one assignment. The bug is hidden in normal use because the `ChocoPy`
   driver appends `"\n"` to every file it reads. Our lexer emits the NEWLINE
   itself.
2. **DEDENT tokens at end of input get invented positions.** The k-th
   DEDENT at the end of the input is located at column k of a line after the
   last line. For
   ```python
   if a:
     if b:
       if c:
         x
   ```
   the reference outputs `Program` and the outer `IfStmt` with location
   `[1, 1, 5, 3]`, although the file has only four lines and line 4 ends in
   column 7; expected would be a position inside the file, e.g.
   `[1, 1, 4, 7]` (the end of `x`). We reproduce this behaviour because our
   output is compared with the reference.
3. **Error messages for DEDENT show the text of another token.** For
   `def f():\n    x:int = 1\n` (function without statements) the reference
   reports `Parse error near token DEDENT: x`; the text after the colon is
   the previous token, not the DEDENT.
4. **The local test mode ignores locations.** With an earlier version of our
   lexer that placed the last DEDENT one column off, `stmt_if.py` produced
   `"location": [1, 1, 4, 0]` instead of `[1, 1, 4, 1]`, but
   `--test` still reported the test as passed. Students may therefore
   believe their locations are correct when they are not.
5. **Specification:** section 6.1.2 calls the kind `NonlocalDecl`, but the
   AST class and all expected outputs use `NonLocalDecl`. Section 2 says
   "stater code" instead of "starter code".
6. **Manual:** section 2.8.6 says "outputs outputs its printed form".
